# Portfolio Design Guardian

Use this skill whenever designing, implementing, modifying or reviewing visible UI for `ramita.dev`.

## Mission

Protect commercial clarity, trust and visual quality for Ramiro's personal commercial website. Help visitors understand the web service, see real evidence and contact the professional.

**Quiet Interactive, Instrument Sans, palette, accents, dark/light and the accent selector are REVISIT**: previously approved V1 material awaiting V2 revalidation, not active mandates.
Read the active product/design documents. Do not revive Concept A, the old H2 flow, a name-led Hero or the absence of a CTA.
The current documentary reset does not authorize UI design or implementation.

The goal is not to make the page look “more designed”.
The goal is to make every visible element feel necessary.

## Before implementing UI

Identify:

1. What is the primary visual focus?
2. Can a nontechnical visitor understand the offer, evidence and contact action?
3. What interaction is actually useful?
4. What can be removed?
5. How will this work on touch?
6. How will it work with reduced motion?

If those answers are unclear and the decision is material, ask before implementing.

## Noise budget

A viewport should normally have no more than 3–4 meaningful visual focal points.

Flag the design if it contains several of these simultaneously:

- giant headline;
- portrait;
- large 3D object;
- multiple project cards;
- stats;
- decorative labels;
- ticker;
- secondary quote;
- HUD elements;
- multiple CTAs.

Reduce before adding.

## AI-pattern check

Challenge any proposal containing:

- bento grid;
- glass cards;
- purple/blue gradient glow;
- blobs;
- excessive rounded cards;
- fake terminal;
- fake operating system;
- tech badges everywhere;
- “50+ projects” style counters;
- decorative coordinates;
- online/status widgets;
- generic floating particles;
- animated grid backgrounds;
- random 3D shapes;
- excessive microcopy;
- tiny all-caps labels used as decoration;
- generic copy such as “crafting digital experiences”.

These are not absolutely forbidden, but require a concrete reason.

## Cards

Do not put content in a card merely to organize it.

First consider:
- whitespace;
- typography;
- alignment;
- rules/dividers;
- image cropping;
- layout.

## Motion test

Every animation must answer at least one:

- What does it reveal?
- What feedback does it provide?
- What hierarchy does it communicate?
- What spatial relationship does it explain?
- What character does it add without competing with content?

If the answer is “it looks cool”, remove it or simplify it.

## Static test

Disable motion mentally or technically.

If the composition becomes weak, fix the composition first.

## Responsive test

Do not port desktop interactions mechanically.

For touch:
- no hover-only information;
- no pointer-following requirement;
- no tiny targets;
- no motion that fights native scrolling.

## Content integrity

Never create realistic filler for:
- projects;
- clients;
- metrics;
- testimonials;
- experience;
- awards;
- locations;
- social profiles.

Use explicit TODO markers internally. PROJECTS.md owns project facts, permissions and attribution; CONTENT.md owns approved public expression. Never imply an agency or nonexistent team, guaranteed business outcomes, unlimited support or unapproved services.

## Review output

When reviewing a UI, return:

### Keep
What is working and should remain.

### Remove
Anything unnecessary or noisy.

### Change
Specific improvements.

### Risk
Accessibility, responsive, performance or “AI-generic” concerns.

### Verdict
One of:
- APPROVE
- APPROVE WITH CHANGES
- REJECT

Do not approve merely because the implementation is technically correct.
